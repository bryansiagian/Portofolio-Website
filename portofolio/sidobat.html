OverviewGambaran Umum

What is SI-DOBAT?Apa itu SI-DOBAT?

SI-DOBAT is a web-based drug distribution and logistics platform developed as a commissioned project for Yayasan Satriabudi Dharma, a foundation managing pharmaceutical distribution in the region. The system replaces a previously manual workflow with a structured, role-based platform.

SI-DOBAT adalah platform distribusi obat dan logistik berbasis web yang dikembangkan sebagai proyek pesanan untuk Yayasan Satriabudi Dharma, sebuah yayasan yang mengelola distribusi farmasi di wilayah tersebut. Sistem ini menggantikan alur kerja manual sebelumnya dengan platform terstruktur berbasis peran.

The platform supports four distinct user roles — Admin, Operator, Courier, and Customer — each with a tailored interface. Customers browse and order medicines, operators approve orders and manage inventory, couriers handle last-mile delivery, and admins oversee everything from user management to financial reporting.

Platform ini mendukung empat peran pengguna yang berbeda — Admin, Operator, Kurir, dan Pelanggan — masing-masing dengan antarmuka yang disesuaikan. Pelanggan menelusuri dan memesan obat, operator menyetujui pesanan dan mengelola inventaris, kurir menangani pengiriman last-mile, dan admin mengawasi segalanya mulai dari manajemen pengguna hingga pelaporan keuangan.

Built as a Laravel 12 microservice architecture with three independent services — auth_service, distribusi_obat, and report_service — each running in its own Docker container and communicating via REST APIs.

Dibangun sebagai arsitektur microservice Laravel 12 dengan tiga layanan independen — auth_service, distribusi_obat, dan report_service — masing-masing berjalan dalam container Docker sendiri dan berkomunikasi melalui REST API.

Problem & SolutionMasalah & Solusi

What we were solving.Apa yang kami selesaikan.

⚠️
The Problem Masalahnya
  • Drug distribution was tracked entirely by hand — orders, stock levels, and courier assignments were done via spreadsheets and phone calls.
  • Distribusi obat dilacak sepenuhnya secara manual — pesanan, level stok, dan penugasan kurir dilakukan melalui spreadsheet dan telepon.
  • No payment tracking: the foundation had no visibility into which orders had been paid, which were pending, or which failed.
  • Tidak ada pelacakan pembayaran: yayasan tidak memiliki visibilitas terhadap pesanan mana yang sudah dibayar, mana yang tertunda, atau mana yang gagal.
  • No audit trail: operator actions (approvals, rejections, inventory edits) weren't logged, creating room for errors and fraud.
  • Tidak ada jejak audit: tindakan operator (persetujuan, penolakan, edit inventaris) tidak dicatat, membuka celah untuk kesalahan dan kecurangan.
  • Multiple teams working in silos — auth, order management, and reporting had no shared system, causing data inconsistency.
  • Beberapa tim bekerja secara terpisah — autentikasi, manajemen pesanan, dan pelaporan tidak memiliki sistem bersama, menyebabkan inkonsistensi data.
✦
Our Approach Pendekatan Kami
  • Designed a microservice architecture — auth, order/distribution, and reporting each as an isolated Laravel service — so each domain could evolve independently.
  • Merancang arsitektur microservice — auth, pesanan/distribusi, dan pelaporan masing-masing sebagai layanan Laravel yang terisolasi — sehingga setiap domain bisa berkembang secara independen.
  • Integrated Midtrans Snap for real-time payment status, with webhook-based updates to keep order state accurate across services.
  • Mengintegrasikan Midtrans Snap untuk status pembayaran real-time, dengan pembaruan berbasis webhook untuk menjaga status pesanan tetap akurat di semua layanan.
  • Built a role-gated operator panel with conditional UI logic (e.g. approve button only visible when payment is confirmed), reducing accidental or unauthorized actions.
  • Membangun panel operator yang dibatasi peran dengan logika UI kondisional (mis. tombol setujui hanya muncul saat pembayaran dikonfirmasi), mengurangi tindakan tidak sengaja atau tidak sah.
  • Implemented a report_service with snapshot tables and event-driven sync so reporting never blocks order processing.
  • Mengimplementasikan report_service dengan tabel snapshot dan sinkronisasi berbasis event agar pelaporan tidak pernah memblokir pemrosesan pesanan.
